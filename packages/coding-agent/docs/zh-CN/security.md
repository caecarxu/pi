# 安全运行 Pi

> 本文为简体中文译本；[查看英文原文](../security.md)。

请将模型生成的命令和代码视为不可信内容。Pi 可以使用启动它的账号权限读取、修改和执行文件，并且不会在每次工具调用前征求确认。除非操作系统或虚拟化边界限制了权限，否则扩展、包安装器、语言服务器和其他子进程也会使用相同权限。

文件、注释、指令、命令输出和模型回复都可能通过提示注入影响模型。项目目录信任决定 Pi 启动时加载哪些项目资源，但它不会对工具调用进行沙箱隔离。

安全性取决于限制 Pi 在生成操作有误或遭到恶意诱导时可访问和影响的文件、凭据、进程及网络服务。查看对话记录、使用项目目录信任和检查变更都不能构成安全边界。

## 选择 Pi 的运行方式

不同运行方式会限制生成命令可访问的资源：

| Pi 的运行方式 | 仍受保护的资源 |
|---|---|
| 直接以操作系统用户权限运行 | 该用户本身无法访问的资源。专用用户账号可以缩小权限范围，但 Pi 仍与其他用户共享操作系统和网络。 |
| 完全运行在容器、虚拟机或沙箱中 | 未暴露给该环境的主机文件和进程。如果将凭据或网络服务提供给隔离环境，它们仍可被访问。通常这是最强的实用隔离方式。 |
| Pi 在隔离环境外运行，仅内置工具在其中运行 | 通过这些工具执行的操作无法触及主机资源。Pi 本身和其他扩展仍在隔离边界之外，因此这种隔离范围较窄。 |

工作目录决定资源发现范围和工具的默认位置，但不会阻止命令访问 Pi 进程本来就能访问的其他路径。

无论选择哪种方式，只提供任务必需的文件和服务。尽可能将凭据留在运行环境之外，或使用权限范围有限、有效期短的凭据。命令不需要网络时，应限制网络访问。

隔离方式的设置步骤及其局限见[在隔离环境中运行 Pi](containerization.md)。

## 了解项目目录信任

项目目录信任决定 Pi 是否加载工作目录提供的大部分设置和资源。它避免项目在你批准前悄悄加载可执行扩展。

项目目录信任并不是完整的启动边界。Pi 在选择或创建会话时、判定项目目录信任之前，会读取项目的 `sessionDir` 设置。拒绝信任会阻止其余项目设置和受保护资源加载，但无法撤销此前对会话目录的初始查询。

项目目录信任不会限制工具调用能访问或影响什么。Pi 启动后，已启用的工具仍使用 Pi 进程的操作系统权限。文件夹中的指令和其他内容也可能影响模型。

### 受项目目录信任保护的资源

如果 Pi 在当前工作目录中发现以下任一资源，就会要求你对项目目录信任作出决定：

- `.pi/settings.json`
- `.pi/mcp.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts` 或 `.pi/themes`
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或其祖先目录中的项目 `.agents/skills`

仅有一个空的 `.pi` 目录不需要项目目录信任。

授予项目目录信任后，Pi 可以加载：

- 项目设置
- `.pi/mcp.json` 中的项目 MCP 服务器
- `.pi` 中的扩展、技能、提示模板、主题和系统提示文件
- 项目设置中声明的缺失包
- 项目本地扩展和项目包中的扩展

拒绝项目目录信任会跳过这些受保护资源，但前文所述的初始 `sessionDir` 查询除外。

### Pi 如何决定信任状态

CLI 参数 `--approve` 或 `--no-approve` 会优先决定信任状态。如果存在受保护资源但没有 CLI 覆盖项，则按以下顺序处理：

1. 用户级扩展和命令行扩展可以处理 `project_trust` 事件。第一个返回 yes 或 no 的扩展拥有决定权。
2. 如果没有扩展作出决定，Pi 会查找当前目录或其父目录的已保存决定，并应用距离最近的决定。
3. 如果没有适用的已保存决定，Pi 会遵循全局 `defaultProjectTrust` 设置，默认值为 `"ask"`。

已保存的决定使用规范化目录路径，并存放在：

```text
~/.pi/agent/trust.json
```

运行 `/trust` 可为后续 Pi 进程保存决定。

### 无交互提示时的项目目录信任

打印、JSON 和 RPC 模式无法显示内置信任提示。如果没有 CLI 覆盖项、扩展或已保存的决定：

- `defaultProjectTrust: "always"` 会加载受保护的项目资源。
- `defaultProjectTrust: "ask"` 或 `"never"` 会跳过这些资源。

自动化运行需要明确的一次性决定时，使用 `--approve` 或 `--no-approve`。

## 降低影响并改善恢复能力

以下做法不能替代隔离，但可以减少暴露面并便于恢复：

- 只授予 Pi 任务所需的文件和服务访问权限。
- 进行重大修改前，使用快照、备份或版本控制。
- 加载扩展和包前先检查；扩展会在 Pi 进程内执行。
- 优先使用权限范围有限、有效期短的凭据。
- 将结果应用到其他系统前，检查 diff 和生成内容。
- 导出或分享会话前先检查，其中可能包含提示、工具参数、命令输出、文件内容，以及对话期间暴露的凭据。

## 报告安全问题

请遵循仓库的[安全策略](https://github.com/earendil-works/pi/blob/main/SECURITY.md)。不要公开提交涉及安全敏感内容的问题。

除非报告证明了权限边界绕过，或访问了本地用户原本无权访问的资源，否则通常不属于安全边界范围的情况包括：预期的本地 Agent 行为、来自不可信内容的提示注入、缺少内置沙箱，以及用户安装的扩展或技能所造成的行为。
